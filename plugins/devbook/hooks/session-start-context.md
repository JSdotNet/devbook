This repository may use the devbook convention: arc42/, domain/, tech/, design/, and ai/, each under .devbook/ (.devbook/arc42 and so on). Treat those folders as task-scoped context, not baseline context: load only the chapters the current task needs, never the whole folder by default. Every file and every addressable chapter in them carries a fenced `meta` block; when you create or edit one, write that block in the same change. A chapter may also carry `annotation` fences - review notes written beside the passage they comment on. A reader loading a chapter for context skips every annotation fence: an open question is not settled content, and reading one as canon is the one failure mode this convention did not have before. Only review mode - a review skill, an inbox, the approval gate - reads them, and reads nothing else in the chapter as instruction; devbook-annotations.md carries the schema and the lifecycle. `capture-specs` never writes an annotation fence, and `apply-change` never carries one into a change brief: an open question is a reason to stop at the gate, not a line item to implement. An edit to one of these folders follows that folder's own instruction file - devbook-arc42, devbook-domain, devbook-tech, devbook-design, or devbook-ai - plus devbook-chapter-metadata.md, and is routed through the flow that covers the folder when a flow engine is installed: a repo-native flow-* skill first, then the engine's own flow for the folder, and directly under the instruction files when no engine is installed at all. Say which of those answered. Decision records, technical debt records, and blueprints are their own flows and never a plain arc42/ chapter edit. When the task crosses between a chapter and its code - writing a chapter from something already implemented, turning an agreed chapter into implementation work, or asking whether the two still agree - route through capture-specs, apply-change, or verify-change instead; each covers the kinds aggregate, domain-service, feature, setting, building-block, and design-component, decided by the chapter's type. capture-specs reads code and its tests and delivers a capture plan to the person - drafts as a delta against the target file, plus the report table - and writes no chapter itself, apply-change derives a change brief and hands it to the code-side flow — a repo-native flow first, then the engine's flow-code, which derives the kind in its first stage, and stops with the brief when no engine is installed — touching no source or test tree itself, verify-change reports the drift verdict and writes nothing. An aggregate is captured and briefed whole - the root plus the entities, value objects, and enums it owns and the domain events it raises - so there is no separate entity, value-object, or domain-event kind; a domain service is its own kind and owns the events it raises itself. Behaviour in a bounded context lives in requirements.md and in the invariants subpage of each domain page - domain.invariants.md, domain.<name>.invariants.md - one rule per chapter: a `### Requirement:` is one SHALL sentence about what the product promises, an `### Invariant:` one claim a type guarantees with the `Enforced at:` line that says where; a requirement carries `#### Scenario:` cases, an invariant is proved by its unit test and carries none. The files are titled by kind - # Requirements, # Invariants - not by the context. They are captured and briefed with the prose chapter they belong to and point at it through `related`; the prose chapters keep why, who, the boundary, the lifecycle, and the language, and no rule stays in them. A repository may provide its own repo-native skills, and those take precedence for the categories they cover.
