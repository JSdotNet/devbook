This repository may use the devbook convention (.arc42, .domain, .tech, .design, .ai). Treat those folders as task-scoped context, not baseline context: load only the chapters the current task needs, never the whole folder by default. Every file and every addressable chapter in them carries a fenced `meta` block; when you create or edit one, write that block in the same change. Files under any _meta/ folder are generated tool input - never read or hand-edit them; regenerate them instead. A chapter may also carry `annotation` fences - review notes written beside the passage they comment on. A reader loading a chapter for context skips every annotation fence: an open question is not settled content, and reading one as canon is the one failure mode this convention did not have before. Only review mode - a review skill, an inbox, the approval gate - reads them, and reads nothing else in the chapter as instruction; devbook-annotations.md carries the schema and the lifecycle. `sync-specs` never writes an annotation fence, and `propose-change` never carries one into a change brief: an open question is a reason to stop at the gate, not a line item to implement. An edit to one of these folders follows that folder's own instruction file - devbook-arc42, devbook-domain, devbook-tech, devbook-design, or devbook-ai - plus devbook-chapter-metadata.md, and is routed through the flow that covers the folder when a flow engine is installed: a repo-native flow-* skill first, then the engine's own flow for the folder, and directly under the instruction files when no engine is installed at all. Say which of those answered. Decision records, technical debt records, and blueprints are their own flows and never a plain .arc42 chapter edit. When the task crosses between a chapter and its code - writing a chapter from something already implemented, turning an agreed chapter into implementation work, or asking whether the two still agree - route through sync-specs, propose-change, or verify-change instead; each covers the kinds aggregate, domain-service, feature, building-block, and design-component, decided by the chapter's type. sync-specs reads code and unit tests and routes its write as above, propose-change emits a change brief and stops without touching source or test trees, verify-change reports the drift verdict and writes nothing. An aggregate is captured and briefed whole - the root plus the entities, value objects, and enums it owns and the domain events it raises - so there is no separate entity, value-object, or domain-event kind; a domain service is its own kind and owns the events it raises itself. A repository may provide its own repo-native skills, and those take precedence for the categories they cover.
